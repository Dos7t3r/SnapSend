# USB 断线后的高 CPU / 高耗电故障

修复版本：v0.5.1，2026-10-07。

## 已确认的根因

v0.5.0 使用 Pipe 接收 iproxy 标准输出/错误，再通过 FileHandle.readabilityHandler 读取并直接丢弃。正常退出处理器负责移除读取器，但主动断线路径先将 terminationHandler 设为 nil，因此这个清理不会执行。

子进程退出后，EOF 仍不断触发读取回调。availableData 返回空数据，处理器却保持注册，形成无等待忙循环。反复断线可能留下多个读取器。这是代码缺陷，不是“缩略图缓存过大”或“轮询间隔稍短”。

修复把本来就忽略的输出直接接到 FileHandle.nullDevice，不创建管道或读取器。进程退出、终止、重连均不再存在该 EOF 回调路径。传输协议、用户照片及配对数据不迁移。

## 复现证据

同机、优化编译、一次短命子进程、3 秒观察窗口：

| 指标 | 原实现 | 修复生产配置 |
| --- | ---: | ---: |
| 输出读取回调 | 2,807,085 | 0 |
| 其中 EOF 空读 | 2,807,084 | 0 |
| 测试进程 CPU 时间 | 2.936210 秒 | 0.000797 秒 |

这证明忙循环及修复效果，但不能直接换算整机耗电、续航或 Activity Monitor 的 Energy Impact。用户原报告发生时 App 已退出，未取得当时线程栈，所以不能保证报告中的全部负载只有此一个来源。

可复现的限时测试（legacy 会刻意占满约一个核心三秒，然后停止）：

```sh
swiftc -O -parse-as-library -module-cache-path build/module-cache Sources/SnapSendCore/USBProxyProcess.swift Tests/Performance/usb-process-benchmark.swift -o build/usb-process-benchmark
build/usb-process-benchmark --legacy
build/usb-process-benchmark
```

## 完整 Mac App 观察

启动实际 v0.5.1（build 7）App，使用现有归档和正常服务，记录进程资源并取两次五秒线程样本。主线程主要在事件等待，未见 FileHandle 空读热点；一次完整样本全部主线程采样都在事件等待。

启动后第一段 20 秒记录：累计 CPU 时间增加 0.78 秒，约相当一个核心的 3.9%；驻留内存在约 51–93 MiB 间波动。另一段活动期间 24 秒：累计 CPU 增加 2.82 秒，期间单次 CPU 点值最高 23.6%，其后空闲点值为 0.0%。取样物理 footprint 为 56.4 MiB、当时峰值 109 MiB。这些是当前窗口下实测，不是全设备、全部课程或长时间上限。

用户确认已连接手机并正常测试后，再记录 24 秒：所有 13 次 CPU 点值均为 0.0%，累计 CPU 时间仅增加约 0.01 秒；驻留内存约 25–30 MiB，没有持续增加。此段只表示观测窗口内空闲，没有把它解释为拍照时的内存上限。

用户随后确认已连接手机并正常测试。测试操作与资源记录不能严格一一对应，完整测试完成反馈仍待确认。此前进程已退出，无法取得同一完整 App 场景的旧版本线程栈作直接对照。

## 仍需确认

最新版在用户原始 USB/Chrome/拍照场景下是否恢复正常，以及长时间内存/能耗。新旧进程必须退出并重新打开修复包，正在运行的旧程序不会因磁盘文件被替换而自动修复。手机锁屏导致断线也是本次重点回归场景。

用户无需重新制造严重高耗电来确认这个已复现问题。修复后正常使用，再观察当前 CPU、能耗及内存；12 小时电源统计会保留此前旧版本的负载，不能要求立刻清零。
